## Decision summary

The best reuse is procedural: copy the workflow ideas into concise, project-specific instructions, while retaining this plan's capability checks, mock/read-only/live separation, tiered approvals, untrusted-input boundaries, Austria focus, and explicit verification. Do not import upstream credentials, scripts, API assumptions, side-effect defaults, or full skill prose. Hermes skills are instructions, not enforcement; real integrations still belong in tools/adapters/plugins.

## Practical fit to Hermes

The current official Skills documentation describes `SKILL.md` with frontmatter, triggers/procedure/pitfalls/verification, platform gating, and exact referenced files; the catalog distinguishes bundled from optional skills. The Hermes repository root license is MIT. This makes upstream Hermes examples the lowest-friction procedural references, but the repo's bundled integrations are not the target project's integrations. Keep each F.R.I.D.A.Y. skill self-contained enough to say what capability it needs and stop cleanly when missing. A local skill alone cannot enforce a hard approval, publish dashboard events, or guarantee read-only behavior.
