# CalDAV calendar adapter

This optional adapter belongs to the separate RogueKI F.R.I.D.A.Y. skill package. It has not been connected to `rogueki/rogue-friday` or a real calendar account.

The Friday installer separately enables `plugins/friday_dashboard_calendar`. That plugin calls only the local Dashboard calendar list route using a calendar-specific private key; it reads the ICS or CalDAV source already configured in Dashboard and does not receive provider credentials. Its model inputs are only timezone-aware start/end times within 31 days. Results are bounded to 100 items, include the oldest validated `fetched_at` timestamp across returned pages, and omit source URLs and descriptions. Invalid or missing fetch times block the result. It does not create, edit or delete events. This bridge does not change the standalone `friday-caldav` adapter contract below.

## Scope

- `adapters/caldav_calendar.py` implements a bounded `calendar-query` `REPORT` for one explicitly named HTTPS calendar collection and account. It requests `DAV:getetag` and `CALDAV:calendar-data`, a VEVENT time range of at most 31 days, and accepts at most 100 calendar objects and 1 MB of response data.
- `mock` reads a labelled synthetic fixture. `read_only` and `live` reads require an explicitly injected authenticated transport. There is no default network transport and no credential lookup.
- One simple VEVENT per calendar object is supported. UTC timestamps, all-day `VALUE=DATE`, and TZID values backed by the host's IANA timezone database can be parsed. Floating/ambiguous/nonexistent local times, recurrence, weak ETags, unsafe XML and objects outside the requested window fail closed. Windows hosts need an IANA timezone source such as Python's `tzdata` package for non-UTC TZIDs.
- The optional Hermes `friday-caldav` plugin registers **one read tool** whose model-visible parameters are only `start` and `end`. `register(ctx)` reads the labelled synthetic fixture by default. Host code may opt into one account by calling `register(ctx, host_read=HostCalDAVReadConfig(...))`; the frozen host config binds `endpoint`, `account`, `allowed_host`, the transport, and explicit `authorized=True` host authorization outside tool arguments. The injected transport must itself attest `authenticated is True`. In that registration, tool calls always use `mode="read_only"`. Model arguments cannot select the account, host, endpoint, or mode. Missing host authorization or transport authentication fails closed. Only successful reads return a fresh `caldav.read` capability record. No write tool is registered.

## Write boundary

The adapter has `write_event` for a caller with a trusted approval gateway. It accepts only `live` create/update. The caller must supply an authenticated transport, a fresh `calendar.write` capability, a host-owned `ApprovalLedger` and one-use grant ID bound to the target, calendar bytes and idempotency key, plus a durable absolute SQLite operation journal path. The old `approval` mapping is no longer accepted. Grant consumption is atomic and occurs before the operation journal reservation and request. Create uses a deterministic `.ics` resource URL plus `If-None-Match: *`; update requires a strong ETag and sends `If-Match`. A pending/uncertain key is never sent again automatically, even after process restart. Reconcile against the server before a new mutation. The operation journal stores the fingerprint and minimal receipt, no calendar contents or credentials. See [approval boundary](APPROVAL_LEDGER.md).

The local ledgers do not prove the caller's identity or the approval's provenance. A production host must own operator identity and authorization, transport authentication, redirect blocking and per-account permissions. The injected transport must reject redirects and enforce the exact allowlisted HTTPS origin. The `authorized` flag and the transport's `authenticated` attestation express that host contract; neither provides authentication by itself. Tests inject a local fixture-backed fake transport only. No provider-specific transport, real credentials, or live calendar endpoint has been verified.

## Status and verification

`python -m unittest discover -s tests -p 'test_caldav_adapter.py' -v` exercises read parsing, time windows, conflicts, approval failures, ETags and replay behavior without network. `python -m unittest discover -s tests -p 'test_hermes_caldav_plugin.py' -v` checks mock-default registration, fixed host binding, auth and authorization failures, request rejection, time bounds, provider errors and the absence of write tools. A provider-specific transport and host authorization gateway remain open work before live use.

Standards: [RFC 4791 CalDAV calendar-query and calendar-data](https://www.rfc-editor.org/rfc/rfc4791.html), [RFC 5545 iCalendar VEVENT/time rules](https://www.rfc-editor.org/rfc/rfc5545.html), [RFC 7232 conditional requests and entity tags](https://www.rfc-editor.org/rfc/rfc7232.html).
