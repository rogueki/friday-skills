# Offline invoice intake and payment preview

`adapters/invoice.py` provides deterministic field review and a **masked, non-executable** payment preview. `adapters/invoice_document.py` additionally reads original digitally generated PDF bytes with pypdf 6.20.1, hashes those exact bytes and extracts unique labelled lines with page/line evidence. Neither module performs network calls, OCR, ledger queries, bank login, SEPA export or transfer. `fixtures/invoices/adapter_invoice.json` and `fixtures/invoices/valid-skonto.pdf` are synthetic. There is no live mode.

## Original PDF intake

Install the pinned parser with `python -m pip install pypdf==6.20.1` before running this optional path. Call `review_invoice_pdf(pdf_bytes, supplier_id="...", trusted_supplier=..., prior_invoice_keys=...)`. The `supplier_id`, supplier record and duplicate index must come from outside the PDF. The document parser accepts at most 2 MB, eight pages, 1 MB decoded content stream per page, 40,000 text characters per page and 120,000 overall. It rejects encrypted or malformed PDFs. pypdf has its own decompression guard; this module checks decoded size before text extraction, but it is **not an OS resource sandbox**. Use host process memory/time limits for adversarial documents.

The parser recognizes exact English/German line labels for supplier, invoice number, dates, service period, net/tax/gross, currency, IBAN, BIC, payment reference and skonto. A field with two occurrences is ambiguous even if both values match. Missing required labels yield `partial`; invalid or ambiguous labels yield `blocked`; values are never guessed. It does not parse tables, multiple invoice items, layouts lacking explicit labels, attachments or image-only scans. It does not run PDF actions or OCR. A text layer on a scan is not proof of accurate OCR.

The output includes `pdf_sha256` for the original bytes and page/line evidence for each recognized field. This hash is **not authenticated sender provenance**. In `read_only`, even if all structured checks pass, the combined PDF review remains `partial` pending visual comparison and independent source authentication. The nested structured review is also downgraded to `partial` for this reason. The only bridge to `prepare_payment` is the pinned synthetic mock scenario below; no live/read-only document can use it.

For plan §31, call with `mode="mock"` only on the exact synthetic `fixtures/invoices/valid-skonto.pdf` bytes. A pinned SHA-256, synthetic supplier ID/record and an empty independent synthetic invoice-key index are all required before `completed` is possible. The fixture result exposes `artifacts[0]["extracted"]` with `currency="EUR"` and `has_skonto=true`; its `actions_taken`, `actions_proposed` and approval lists remain empty. Rebuilding a PDF with identical visible labels but different bytes fails the fixture gate. Mock completion says only that this known fixture passed local checks; it makes no claim about sender authenticity, Dashboard delivery or payment execution.

## Input and evidence boundary

Required strings: `supplier_id`, `supplier`, `invoice_number`, `issue_date`, `due_date`, `net`, `tax`, `gross`, `currency`, `iban`. Money is exact decimal text with two fractional digits; dates use `YYYY-MM-DD`. EUR is the only supported currency. IBAN length checks currently cover AT, BE, CH, DE, ES, FR, GB, IT, LU, NL and PL; other country codes fail closed. The check-digit calculation uses MOD-97, as described in [SWIFT's IBAN reference](https://www.swift.com/resource/iban-registry-pdf). A valid checksum does not establish account ownership or invoice legitimacy. Optional `tax_rate_percent` is checked against net and tax. Optional discount requires all three of `discount_percent`, `discount_base` (`net`/`gross`) and `discount_deadline`.

For the structured-field route, the host must separately prove that fields match the original invoice, identify pages/confidence, and retain document provenance. Its result sources contain `urn:sha256` fingerprints of the caller's structured field object and, when supplied, the supplier record and invoice-key index. These are **not** hashes or signatures of an original PDF or proof of independent provenance. Source data and document instructions are untrusted. No source text appears in error codes.

`prior_invoice_keys` must be an independently sourced set of `duplicate_key(supplier_id, invoice_number)` values. An empty set means the caller has a complete index with no match; `None` means lookup is unavailable and review is `partial`. The host must enforce the index's scope, freshness and completeness. The key does not use supplier name as identity.

`trusted_supplier` must be an independently obtained record containing `source_kind: independent_supplier_record`, matching `supplier_id`, matching supplier name and a valid IBAN. The adapter checks equality but cannot prove that the host obtained the record independently. An invoice-provided or missing record cannot establish bank-detail trust. Changed bank details or supplier name, duplicate key, invalid IBAN, wrong totals, date order and discount inconsistencies block review.

## Local preparation

`prepare_payment` reruns review and prepares a masked preview only after review is `completed`. An intended date before the invoice issue date blocks the preview. It calculates `discount = round(base * percent / 100, cents)` if the date is on or before the discount deadline. The preview shows gross, discount, amount, date, reference, beneficiary and a masked IBAN. Source retrieval timestamps are normalized to UTC. Its `actions_taken` only records creation of the local preview. No payment is proposed as executed or authorized. Payment execution remains Tier 3 in a separate future banking gateway.

## Plan §32 E2E 2 local mock

`run_scenario("invoice_pdf_to_payment_draft")` reads the actual pinned PDF bytes, loads a separate synthetic supplier record and invoice-key index, calls `review_invoice_pdf(..., mode="mock")`, and passes the extracted fields to `prepare_payment` only after `completed`. It returns the masked `non_executable_payment_preview`, skonto and due-date facts, local started/completed lifecycle events and `dashboard_mapping` entries with `publishable=false`. The intended date 2026-10-15 gives EUR 116.62 after EUR 2.38 skonto; `variant="after_discount_deadline"` uses 2026-10-21 and gives EUR 119.00. `altered_pdf`, `duplicate_invoice`, `changed_supplier_bank`, `missing_invoice_index` and `missing_supplier_record` block before payment preparation. The scenario has zero external effects and an empty action audit. No Dashboard publication, banking handoff or payment execution occurs.

## Verification

Run `python -m unittest discover -s tests -p test_invoice_adapter.py -v` and `python -m unittest discover -s tests -p test_invoice_document.py -v`. The latter parses the actual `valid-skonto.pdf` bytes, checks the §31 mock outcome and a changed-byte same-label negative, and exercises duplicate/bank discrepancies, missing and ambiguous fields, image-only, invalid, encrypted and oversized inputs. Tests use no provider, credential or network access. Real-world layout accuracy, authenticated sender and supplier/ledger provenance remain unverified.

For §32 E2E 2, run `python -m unittest discover -s tests -p test_scenarios.py -v`. This proves only the local composition of the actual PDF and payment adapters with synthetic records and local event mapping. It does not verify the separate `rogue-friday` application or its Dashboard.
